# 招聘截图两阶段识别设计

## 目标

把招聘截图识别拆成“提取文字”和“分析岗位信息”两个阶段，避免视觉模型虽然读出正文，却因为结构化字段格式不稳定而让整次识别失败。

## 范围

- 沿用现有图片上传入口、数量和大小限制。
- 第一阶段使用已配置的视觉模型，按图片顺序提取完整文字并保留标题、列表和段落顺序。
- 第二阶段使用通用文字模型，从第一阶段文本中提取公司、岗位、城市、招聘批次、职位链接和 JD。
- 缺失字段返回空字符串；只要至少识别出一个有效字段，就把可用结果填入表单。
- OCR 文本只在请求处理中临时传递，不写入数据库或文件存储。
- 不增加新的 OCR 服务、账号或环境变量。

## 数据流

1. 浏览器压缩用户选择的图片并按当前顺序上传。
2. 服务端验证图片格式、数量、单张大小和总大小。
3. 视觉模型返回按图片编号组织的原始文字。
4. 服务端拒绝空白或明显不可用的 OCR 结果。
5. 通用文字模型分析 OCR 文本，返回岗位字段、逐字段可信度和识别提示。
6. 服务端兼容常见模型差异，包括缺少字段、单个可信度数值、数字字符串和字符串形式的提示。
7. 前端沿用现有规则：空白字段自动填入，已有内容产生冲突选择，不覆盖用户输入。

## 错误处理

- 第一阶段失败时提示“图片文字识别失败”，建议检查清晰度或重新上传。
- 第二阶段失败时提示“已识别图片文字，但岗位信息分析失败”，允许用户重试。
- 模型缺少非必要字段时使用空字符串或零可信度，不让整次请求失败。
- OCR 没有任何文字，或分析结果没有任何可用字段时才判定为失败。

## 验证

- 单元测试覆盖 OCR 响应为空、结构化响应缺少字段、可信度为单个数字、提示为字符串等情况。
- 使用现有中文 JD 测试图执行真实两阶段调用，确认能提取正文并填入至少一个岗位字段。
- 运行类型检查、测试和 Cloudflare 构建。
- 桌面和 390 像素宽手机视口复测原有上传与填表流程。

## 非目标

- 不保存完整 OCR 中间文本。
- 不接入第三方专用 OCR 服务。
- 不改变图片原件的保存与访问权限。
- 不改变 AI API Key 的服务器端配置方式。
