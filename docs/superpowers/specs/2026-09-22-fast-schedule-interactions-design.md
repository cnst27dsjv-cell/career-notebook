# 快速日程交互优化设计

## 背景

当前工作台在登录后需要等待 `/api/data` 全量数据返回才显示页面。日程保存、勾选完成和删除操作也会在服务端写入后再触发全量刷新，网络慢时用户会看到明显等待，并且容易误以为需要手动刷新。

## 目标

- 登录进入工作台时减少“卡住”的感受，保留真实数据加载与登录校验。
- 新增、编辑、完成和删除日程后，界面立即反映变化。
- 服务端写入失败时给出提示，并恢复到可靠状态。
- 不拆分现有 API，不改数据库结构，不影响投递、简历、资料库等其他业务。

## 方案

优先实现前端乐观更新。`Workspace` 增加一个本地数据更新入口，在发起 `/api/data` 写入前先保存当前数据快照并立即更新 `data.events`。请求成功后后台刷新一次用于校准；请求失败时回滚快照并提示错误。

日程表单保存后直接关闭弹窗，并把保存后的日程写入本地列表。为了让前端有准确数据，`event.save` 返回保存后的事件对象。完成和删除操作使用当前页面已有的事件数据即可完成乐观更新：完成时只改状态，删除时从列表移除。

登录加载保留现有鉴权流程，不在这次引入缓存登录。只优化加载状态与刷新去重，避免同一时间重复拉取 `/api/data`。

## 数据流

1. 用户点击保存、完成或删除。
2. 前端立即更新本地 `data.events`，页面随即变化。
3. 后台提交 `/api/data`。
4. 成功后静默刷新一次，补齐服务端生成的版本号、提醒任务和关联投递状态。
5. 失败时恢复操作前数据并显示错误提示。

## 错误处理

- 表单校验、时间冲突、版本冲突等服务端错误会回滚本地变化。
- 登录过期仍按现有逻辑跳转到登录页。
- 后台校准刷新失败时保留当前页面状态，并提示“已保存，但页面同步失败，请稍后重试”。

## 验证

- 单元测试覆盖事件保存返回值和完成/删除行为。
- 手动验证：新增日程、编辑日程、勾选完成、删除日程后页面无需手动刷新。
- 生产部署前运行 `npm test`、`npm run typecheck`、`npm run build:vinext`。
