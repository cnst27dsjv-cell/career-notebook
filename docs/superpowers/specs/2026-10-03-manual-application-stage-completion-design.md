# 投递阶段手动完成设计

## 背景

投递记录的“阶段状态”目前完全由关联日程自动计算：没有日程时是“待安排”，存在待完成日程时是“待完成”，完成关联日程后是“等待结果”。这个规则无法表达“新建投递记录时，测评、笔试或面试已经完成”的真实情况。

## 目标

用户可以在新建或编辑投递时手动标记当前测评、笔试或面试阶段已完成。标记后保留当前阶段，明确显示“已完成 · 等待下一阶段”，不自动推测下一个招聘流程。

## 交互设计

- “测评”“笔试”“面试”阶段的状态区增加“该阶段已完成”开关。
- 未勾选时，状态继续根据当前阶段的关联日程自动显示“待安排”或“待完成”。
- 勾选时，状态区立即预览“已完成 · 等待下一阶段”。
- 保存后当前阶段不变。例如，“测评”不会被自动改成“笔试”。
- 用户后续手动把阶段改成“笔试”或“面试”时，新阶段重新按关联日程计算“待安排/待完成”，不继承上一阶段的完成状态。
- “待投递”“已投递”和“Offer”保持现有规则，不显示该开关。

## 数据与规则

- 复用 `Application.stageStatus` 存储结果，不新建独立阶段表。
- 手动完成的测评、笔试和面试统一保存为“等待结果”。状态主文案统一显示“已完成”；测评和笔试的说明显示“等待下一阶段”，面试的说明显示“等待面试结果”。
- 保存请求增加明确的手动完成标记。服务端只对测评、笔试和面试接受该标记，避免伪造其他阶段状态。
- 对同一投递、同一阶段，如果存在“待完成”的关联日程，手动完成时将该日程同步更新为“已完成”。
- 新建投递时，如果用户同时填写了该阶段的日程时间并标记阶段已完成，则创建一条“已完成”日程，用于保留历史时间，不创建提醒任务。
- 被同步完成的日程不再触发未发送的提醒；相关 `pending` 或 `sending` 通知任务改为 `cancelled`。
- 新建记录时可以在没有日程的情况下直接保存手动完成状态。
- 如果用户取消“该阶段已完成”，状态重新根据当前待完成日程计算。此操作不自动恢复已经标记完成的日程，避免重新启用过期提醒；需要恢复日程时由用户在日历中单独处理。

## 一致性与错误处理

- 投递状态和日程完成在同一数据库事务内保存，任一步失败时整体回滚。
- 保持现有版本号冲突检查，防止其他设备的更新被覆盖。
- 数据读取时保留已保存的“等待结果”，不因为没有待完成日程而重新降级为“待安排”。
- 手动完成和日程自动完成使用相同的最终状态，避免列表、编辑窗口和导出结果不一致。

## 不在本次范围

- 不根据完成动作自动推测下一阶段。
- 不增加“已测评”“已笔试”“已面试”三个独立阶段。
- 不重构为完整的多轮招聘流程模型。

## 验收标准

1. 新建一条“测评”阶段的投递，不填日程并勾选“该阶段已完成”，保存后显示“测评 · 已完成，等待下一阶段”。
2. 编辑已有待完成测评日程的投递并勾选完成，投递状态和日历中的测评均显示已完成，未发送提醒被取消。
3. 将上述投递的阶段改为“笔试”，未安排笔试时显示“待安排”，不继承测评的完成状态。
4. 对“待投递”“已投递”或“Offer”不显示手动完成开关。
5. 同时打开两个设备修改同一条投递时，保留现有版本冲突提示，不静默覆盖数据。
