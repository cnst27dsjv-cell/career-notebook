# 日程与投递保存性能优化设计

## 问题

新增日程和新增投递在保存后会等待完整工作台数据刷新。完整刷新会读取投递、日程、简历、面试资料、文件和提醒记录等多类数据。当数据库为远程 Supabase 时，用户会看到弹窗长时间停留在保存状态。

带日程的投递和新增日程还会在事务内执行关联记录查询、冲突检查、状态同步和多条提醒任务写入，当前提醒任务逐条写入，增加了远程数据库往返次数。

## 目标

- 保存 API 成功后立即结束表单提交和关闭弹窗。
- 完整工作台数据在后台刷新，不阻塞弹窗关闭。
- 实际保存路径减少可避免的 Supabase 往返。
- 保留所有权校验、版本冲突检查、日程冲突检查和投递状态同步。

## 前端行为

`Workspace.mutate` 仍会等待写入 API 返回，只有写入真正成功后表单才结束提交。写入成功后，完整数据刷新改为后台执行，刷新失败时显示提示，但不把已成功的保存误报为失败。

投递表单因需要在获取新投递 ID 后上传图片，仍等待当前已选图片上传完成。没有待上传图片时，不再等待全量刷新。图片上传失败时仍保留表单和失败图片，便于重试。

## 后端优化

- 提醒任务使用 `createMany` 一次写入，取代事务内的逐条 `create`。
- 投递保存复用已查询的待完成关联日程，不再在同一事务中重复查询。
- 冲突检查只读取 `id`、`start` 和 `end` 等必要字段。
- 编辑记录时，尽可能在事务内一次取得记录并同时完成所有权与版本校验，不在事务前后重复读取。

## 错误与一致性

不采用未确认的乐观保存。API 返回前，应用、日程和提醒任务仍在同一数据库事务中完成。冲突、过期提醒、记录不存在或版本已变更时，弹窗保持打开并显示原有错误。

后台刷新期间如果用户继续操作，下一次刷新可以覆盖旧结果；通过一个共享的刷新 Promise 避免同时发起多个重复全量请求。

## 验证

- 单元测试覆盖提醒时间转批量数据和空提醒情况。
- 集成测试覆盖新增日程、新增投递、投递关联日程及冲突拒绝。
- 记录优化前后的保存 API 耗时和弹窗关闭耗时。
- 运行全量测试、TypeScript 检查和 Vinext/Cloudflare 构建。
