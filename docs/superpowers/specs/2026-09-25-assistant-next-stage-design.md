## 1. 结论与设计假设

当前产品已有真实的 AI 提取、分类、润色和模拟面试能力，也有较完整的业务数据与保存规则；但“助理”本身还是一次性输入工具，没有持续对话、跨模块行动计划、长期记忆或主动复盘。

推荐优先上线**聊天办事型助理**：理解用户表达、读取相关资料、追问必要信息、生成可审阅行动草稿，用户确认后一次完成关联操作。再在这套可信执行基础上接入面试教练和主动复盘。

暂定假设：继续单账号产品、北京时间、现有纸质手账风格；优先减少重复录入和页面跳转；正式业务数据变更一律先审阅；站内主动提示先行，外部通知单独开关。已向用户询问“聊天办事 / 面试陪练 / 主动督促”的优先级，尚未收到答复时以聊天办事为方案默认，不视为用户已批准。

本方案只设计移动端交互行为，不制作视觉稿。三个独立交付包为：可信聊天与执行、面试准备与复盘、主动跟进与长期理解。可以依次上线，不需要一起重写。

## 4. 三条路线与推荐选择

| 路线 | 收益 | 代价 | 决定 |
| --- | --- | --- | --- |
| A. 在现有模块上加持续聊天和受限行动草稿 | 复用数据、表单和规则；能验证“一句话办事”；风险边界清楚 | 需先做草稿持久化、统一执行和上下文选择 | **推荐 MVP** |
| B. 先把面试准备做成专业教练 | 能快速改善回答质量和复盘体验 | 新建/改期仍靠跳页面，助理总体割裂 | 作为 A 之后的第二包；若用户更看重陪练，可调换产品交付顺序但保留执行基础 |
| C. 直接建设自主长期 Agent | 可覆盖广泛任务与主动行为 | 权限、长期任务、评估、成本和恢复面显著扩大 | 本阶段不采用；无需新 Agent 框架、多代理或向量数据库 |

“像真实助理”的判断标准：记得正在处理哪件事；知道资料来自哪里；遇到不确定会追问；能把讨论变成明确行动；做完说明实际结果；下次跟进有理由。增加拟人语气不能替代这些能力。

## 5. 聊天意图与跨模块任务

| 意图 | 例子 | 上下文 | 输出和边界 |
| --- | --- | --- | --- |
| 查询与解释 | 明天有什么？这家公司进展怎样？ | 时间范围、投递、关联日程 | 直接答，列来源和读取时间，不改数据 |
| 新建投递/收藏 | 把这段 JD 建成投递记录 | 粘贴内容、相似投递、选定简历 | 生成新建草稿；默认待投递，实际投递时间不能猜 |
| 修改投递 | A 公司通知我进入二面 | 公司/岗位/批次、现阶段 | 生成差异；多岗位先选，不推断最终通过 |
| 新建/修改/完成日程 | 把一面改到下周四 15 点 | 明确场次、现日程、来源时间 | 改期草稿而非新增；完成需展示阶段和提醒的连带变化 |
| 安排准备 | 面试前帮我留一小时练习 | 面试、空闲、截止、时长偏好 | 确定性找空档，用户选后生成日程草稿 |
| 面试准备 | 用这份 JD 和投递简历帮我准备 | 当前 Preparation、JD、实际投递版本、已确认材料 | 准备提纲、资料候选、缺口；确认后创建准备/复用副本 |
| 练习与润色 | 追问这个项目；把回答说得清楚一点 | 当前题目、原回答、用户明确补充 | 建议稿；不能把推测经历写入正文 |
| 实际面试复盘 | 刚面完，问了三个问题 | 对应 Event、用户回忆、原准备 | 先记录原话，再提炼表现/缺口，确认后入库和安排行动 |
| 每日/每周计划 | 帮我看看本周卡在哪里 | 完成和阶段历史、截止、前次承诺 | 确定性统计＋有依据建议；排期仍为草稿 |
| 记忆与偏好 | 以后优先上海岗位 | 用户明确陈述、旧偏好 | 显示将记住的内容，确认后作为长期偏好 |
| 更正、放弃、重试 | 不是这家公司；不要保存；重试刚才那项 | 活跃任务、草稿版本、执行回执 | 纠正目标或作废旧草稿；不能重放已完成动作 |

首版支持表内查询、新建/修改投递、新建/修改/完成日程，以及建立面试准备和有限资料复用。复杂陪练、正式复盘和长期记忆进入后续包。未知意图返回可用方式和手动入口，不能默默退化为日程提取。

### 5.1 一次对话的完整例子

用户：“A 公司产品岗下周四下午三点二面，帮我安排一下，前一天准备一小时，用我投递的简历。”

1. 找出 A 公司匹配岗位，读取实际投递简历版本、现有面试日程和准备；如果有多个岗位或多场面试，给出候选供选择。
2. 日期依据当前北京时间及消息来源。粘贴旧通知时询问通知日期；固定面试缺少结束时间则不伪造，用标注的预计占用时长计算冲突。
3. 查询前一天空档；若未确认可用时间，只询问偏好。现有场次明确是改期则更新该场，不新建。
4. 生成一组可审阅动作：更新投递阶段；新建/修改二面日程；新建准备时段；建立或关联面试准备；引用实际投递简历。明确列出每项关联、提醒和已有资料。
5. 用户可排除准备时段，系统重新计算依赖并展示修订后的整组草稿。依赖必需项被排除时，对应子项不可单独执行。
6. 用户确认后服务器一次事务写入所有选中业务记录及提醒，返回真实 ID。助理回复“已安排”，附可打开的记录；不能在生成草稿时说“已完成”。

MVP 每组最多 5 个正式写操作；超过时建议分组，不静默截断。一个对话可以连续处理多项任务，但不同岗位以清晰的上下文标签切换；“它”“刚才那个”只能在当前明确绑定的对象上解析，存在歧义就追问。

## 6. 上下文：取相关、可追溯的资料

上下文顺序：当前用户消息与入口明确选择 → 当前活跃草稿及最近对话 → 实时业务记录 → 用户确认的长期事实 → 检索材料。聊天中的新陈述可用于本次建议，但未确认前不能覆盖数据库事实；出现矛盾要并列展示并询问。

| 数据 | 如何使用 | 保真规则 |
| --- | --- | --- |
| 日历 | 目标事件与请求范围内未完成占用、截止、不可用时段 | 保存前重查；默认查询未来 7 天，可按请求扩大并标明范围 |
| 投递 | 目标岗位、批次、阶段、历史、实际投递时间、简历引用 | 不能按公司名唯一定位；不能把收藏视为已投递 |
| JD | 优先当前准备的 JD 快照；没有则从关联投递取并提示来源 | 冲突不静默合并，记录来源版本/内容哈希 |
| 简历 | 先使用实际投递版本；用户选择其他版本时标明差异 | 首版仅元数据＋用户粘贴且确认的相关经历；没有正文就明确未读简历 |
| 材料 | 当前准备材料、用户选择的历史回答、相关通用经历 | 返回 ID、版本、来源和节选；草稿不混入正式材料检索 |
| 模拟/真实面试记录 | 用于追问、缺口对比和复盘 | 模拟表现与真实面试结果分开，不能推断面试官评分 |

检索先修正“只查最近 100 条”的范围：在当前账号全量已确认材料中按岗位类别、标题和关键词过滤，再限量排序。首版无需 embedding；增强版用固定中文样例测同义召回，再决定是否增加数据库文本相似度或模型重排。

每次输出提供折叠的“依据”：如投递记录、日程、材料版本、用户某条消息；同时显示“本次未读取简历正文”。数据库来源必须是服务端实际返回的 ID，模型不能自行编造引用。对话摘要保留目标、决定、未解问题和来源；摘要只是压缩上下文，不能成为新的事实来源。

## 7. 草稿确认、风险边界与可靠执行

### 7.1 哪些直接做，哪些必须确认

| 类别 | 操作 |
| --- | --- |
| 可直接执行 | 当前账号内只读查询、统计、建议、生成临时提纲；已告知规则下自动保存聊天与未确认草稿；取消尚未执行的草稿 |
| 明确按钮即可执行 | “稍后提醒”“忽略这条建议”等局部可逆 UI 状态；仍记录操作，不借此改变正式日程 |
| 必须审阅并确认 | 新建/修改/完成/取消日程，更新投递，绑定简历，建立准备，材料入库/修订，长期记忆和提醒偏好变更 |
| 单独确认，不并入普通批次 | 删除数据、彻底忘记及衍生内容清理、覆盖存在冲突的时间；MVP 不提供聊天批量删除 |
| 不在本阶段 | 自动投递、代发招聘方消息、自动接受 Offer、自动读取邮箱；外部发送始终有明确权限边界 |

这里的“直接执行”不包含模型推断的业务变更。即便“标记完成”可撤销，也会影响投递阶段和提醒，仍要展示紧凑确认卡；用户点卡片“确认完成”即是确认，不再弹第二次相同询问。

### 7.2 草稿内容及状态

草稿卡列出对象、动作、前后值、来源、缺失信息、冲突、提醒变化和依赖。字段可编辑；编辑或补充消息生成新 revision，旧 revision 不可再确认。MVP 用按钮确认，聊天中的“好的”只引导到当前确认卡，避免含糊授权。

状态：`needs_input → ready → applied`；并列终态为 `rejected / expired`，版本冲突进入 `conflicted`，失败保留可重试状态和错误。数据库事务内部可以标记 applying，但不把它当作持久后台队列；执行失败整体回滚到可重试草稿。

就绪草稿默认 24 小时有效；过期后保留内容，重新校验并生成新版本。准备日期、对象版本、资料删除、用户取消都可使草稿失效，不仅检查时间。

### 7.3 执行协议

1. 确认请求仅提交 draftId、revision、planHash、幂等键；使用服务器保存的动作清单，不接受客户端任意改写。
2. 鉴权并检查所有对象的 userId、允许动作及参数。验证目标版本、引用仍存在、关键缺失为零、用户勾选的冲突授权仍匹配同一计划。
3. 在短事务内按用户锁执行；重查日程占用、重复候选及对象版本。校验实际将变更的所有对象，包括日程联动的 Application。
4. 一次提交投递、历史、日程、提醒队列、准备/材料，以及草稿 applied 状态与结果 ID。任何一步失败全部回滚；事务内不调用模型、网页、邮件或文件上传。
5. 同一幂等键和相同内容返回原回执；相同键不同内容拒绝。同一草稿已 applied 即使换键也返回原结果。并发确认通过锁和唯一约束只提交一次。
6. 网络断开时客户端按 draftId 查询结果；不生成新草稿重放。版本冲突展示“你确认后将改动的值 / 当前新值”，需重新审阅。

执行模型不直接调用 `/api/data` 多次拼成伪事务。只提取当前需要的业务函数，接受 Prisma TransactionClient，让旧路由和助理共用；避免两套联动规则。Preparation 增加 version 并让旧表单也提交版本，否则助理的版本保护会被旧路径绕过。

### 7.4 重复与恢复

技术重试去重靠幂等键和已提交回执；语义重复靠公司/岗位/批次、事件类型/时间/轮次、来源哈希查候选，两者不能相互替代。语义相似只提示，允许用户明确选择“另一条记录”；不强制唯一公司岗位。

“撤销”生成逆向差异草稿，检查提交后对象版本；有新编辑就不能一键回滚覆盖。已经发出的邮件不能撤回。模型超时保留消息和草稿，不自动执行；格式失败最多一次结构修复；权限和数据校验错误不盲目重试。

## 8. 主动提醒与复盘

主动能力分成“规则发现机会”和“用户进入后生成建议”。Cron 只按事实生成轻量提示，默认不在后台反复调用模型。

| 场景 | 建议触发规则 | 内容及结束条件 |
| --- | --- | --- |
| 每日计划 | 开启后本地 09:00，每日一次；当天有安排/截止/逾期才生成 | 最多 3 个重点及依据；无变化不反复推送 |
| 每日复盘 | 开启后 21:00；当日有完成、状态变化或未完成计划 | 一次问一个问题：完成了什么、卡点、明天一步；回答可生成行动草稿 |
| 每周复盘 | 开启后周日 20:00，每周一次 | 本周实际投递、阶段推进、完成、逾期与下周压力；无活动显示资料不足，不虚构趋势 |
| 面试前准备 | 待完成面试距开始 24 小时且缺准备；临近创建则立即形成站内卡 | 当前 JD、实际投递简历、可复用材料、三个缺口；已准备/取消则撤掉 |
| 面试前速览 | 用户开启后，面试前 2 小时 | 已确认准备摘要；与普通日程提醒合并呈现，避免双重打扰 |
| 面试后复盘 | 明确标记完成后 30 分钟；仅时间经过时询问“是否已结束” | 不自动标完成。问题、原回答、困难、下次行动；已复盘或拒绝不重复 |
| 等待结果跟进 | 用户设定期待回复日，或接受建议日期 | 提醒自行跟进；不自动发给招聘方、不将沉默判为失败 |

以上时间是可调整的产品默认提议，不是已有用户偏好。首版可只提供首页规则卡，外部邮件仍沿用用户现有日程提醒。增强版首次开启主动提醒时选择类型、时刻和渠道，默认站内；邮件需验证邮箱并明确开启。

去重键使用 userId＋规则类型＋目标 ID/本地日期或周；事件版本变化时更新同一提示并取消旧待发送项，不因每次编辑重新刷一条。保存 eligibility、dueAt、expiresAt、snoozedUntil、dismissedAt、resolvedAt、lastDeliveredAt 和依据版本。普通主动通知每天最多 1 封汇总，默认 22:00—08:00 不发；用户明确配置的关键日程提醒继续遵守原设置，不套此静默限制。

周复盘窗口固定为北京时间周一 00:00 至周日结束，统计展示截止读取时刻；用历史区间统计而非把当前 stage 当作本周变化。样本少时只描述事实，不给虚假的成功率归因。

Cron 停机恢复：每日卡只保留当前有效周期，不补发数日旧复盘；面试前提示超过开始时间作废，面试后提示保留 48 小时再归档。站内触发不依赖 Resend；需拆开当前 worker 在邮件未配置时直接退出整个 scheduled 的限制。

Cloudflare Cron 按 UTC 运行，业务周期由 Asia/Shanghai 计算；保持每分钟扫描数据库到期项，不按每个用户新建 Cron。[官方说明](https://developers.cloudflare.com/workers/configuration/cron-triggers/)。不将触发频率等同于手机通知到达承诺。

## 9. 持续理解、记忆与隐私

记忆分三层：本次对话（当前对象与待解问题）、业务事实（投递/日程/资料是唯一正式来源）、用户确认的长期偏好/经历。避免从聊天自动生成不可见画像。

“以后主要看上海产品岗”生成记忆建议卡；确认后保存偏好、原消息来源、确认时间、适用范围。暂时忙碌或一次失败不推断为长期能力/性格。矛盾记忆展示新旧内容并要求选择；旧事实标 superseded，停止召回。

增强版提供“助理记住了什么”：查看、修改、删除、停用记忆。目标城市和求职阶段每 30 天询问是否仍有效；临时安排按截止过期；已确认经历不自动改写。记忆 confidence 仅辅助排序，不能替代确认。

会话默认保留 90 天，未确认草稿 30 天后清理，已采用结果保留业务引用与执行元数据；这些是建议默认值，启用时明示。临时对话不形成长期记忆，结束后 24 小时内清理正文；若确认业务写入，明确告知该业务记录会保留。

删除会话时同时失效其未采用草稿、摘要与未确认记忆候选；已确认资料/记忆是独立副本，列出清除范围，不能声称删聊天就删了所有衍生数据。个人数据删除必须清理缓存与未来模型上下文；审计回执只保留无正文的动作元数据。备份保留期在生产实际策略核对后告知，不能沿用旧文档就宣称已经执行。

模型调用只发送当前任务所需片段，简历联系方式默认不发送；搜索只使用公开公司、岗位和技能词。上传文件与点击“供助理分析”分开；原始文件继续私有鉴权。外部文档、网页、图片文字只作为资料，不得改变工具权限。所有动作都经过服务器白名单与归属校验，即使模型遭提示注入也不能越权写入。

沿用 Better Auth＋服务端 Prisma，不增加浏览器直连 Supabase 的新访问面；核实专用项目 Data API 关闭。若未来确需开放 Data API，再按实际认证模型设置授权和 RLS，不能直接套用本项目并未采用的 Supabase Auth 用户映射。[Supabase 官方说明](https://supabase.com/docs/guides/api/securing-your-api)。本轮未访问控制台；changelog.md 读取失败，涉及新 Supabase 功能时须在实施阶段重新核对。

## 11. 接口与内部模块

| 接口 | 合约 |
| --- | --- |
| POST /api/assistant/conversations | 创建会话；可传当前页面对象引用，服务器验证归属 |
| GET /api/assistant/conversations/:id | 分页消息、活跃草稿、上下文标签；用于跨设备恢复 |
| POST /api/assistant/conversations/:id/messages | clientMessageId、text、contextRefs；持久化输入，返回回答/澄清/草稿引用；重试不能重复消息或执行 |
| GET /api/assistant/drafts/:id | 返回最新 revision、校验状态及真实执行回执 |
| PATCH /api/assistant/drafts/:id | 基于 revision 修改草稿或选中动作，重新校验、生成 planHash |
| POST /api/assistant/drafts/:id/confirm | revision＋planHash＋幂等键；原子提交并返回 affectedEntities 和各版本 |
| POST /api/assistant/drafts/:id/reject | 作废未执行草稿；已 applied 不作伪撤销 |
| GET/PATCH /api/assistant/signals | P1：获取、忽略、稍后、解决提示；不能借此更新日程 |
| GET/PATCH/DELETE /api/assistant/memories | P1：查看、确认/更正、清除记忆；含版本检查和衍生清理范围 |
| POST /api/assistant/reviews | P1：保存真实面试复盘草稿；正式入库走统一确认协议 |

错误约定：401/403 鉴权；404 不暴露其他账号对象；409 版本/幂等冲突；422 缺字段或日期/依赖校验失败；429 达额度；模型不可用返回明确错误码和手动退路。成功不能只返回一段“已完成”文案。

内部只新增所需职责：context 负责读取与证据，planner 负责受限意图/草稿，validator 负责日期/依赖/冲突，executor 调共享业务写函数，signals 负责规则触发。模型生成自由文本和动作提议，服务器负责动作权限、ID、时间与最终执行。

不把现有近千行 data 路由全量重构作为前置。先提取本次会用到的 application/event/preparation/material 写入函数，保留其他功能和 API；用回归场景验证旧界面行为不变。

## 12. 模型与成本控制

复用现有 DeepSeek 通用文本配置用于意图/提取/短总结，polish 配置用于用户主动请求的深度润色或复盘；Tokendance 只在用户提交图片时调用。联网搜索单独配置、显式触发，不把文本模型当成实时搜索。

MVP 不让模型无限循环：每轮通常一次规划调用；需要补充上下文时最多两次；结构修复最多一次并计入总计三次上限。确定性日程查询和统计不必调用模型。长任务先列缺口，不自动升级到昂贵调研。

建议起始保护值：最近 12 条消息＋已验证摘要；最多 10 个候选材料、总上下文上限约 12k tokens、单次输出上限约 2k tokens；超出时显示使用节选，保留来源。具体 token 预算按接入模型实测调整，不把字符数当精确 token。

每天建议上限 30 次通用生成、5 次深度生成、3 次图像识别；这是初始产品阈值而非当前服务价格。用户可调低/关闭；请求前预留并发额度，失败释放未产生的配额，已被供应商计费的失败尝试仍记账。金额预算按核对过的模型价格配置，价格未知时仅使用请求/token 限额，不显示虚假人民币费用。

缓存以用户＋目的＋输入/来源版本＋promptVersion 为键，模型变更也失效；事务执行前仍必须重查实时记录。删除资料立即失效缓存。站内主动卡由规则生成，打开后才按需生成正文；超预算仍保留手动管理、统计和日程提醒。

## 13. 移动端交互

保持现有奶油纸、酒红和触控规范，不增加复杂控制台。全局助理入口保留；从日程/投递/准备进入时自动带一个可移除标签，如“A 公司 · 产品岗 · 二面”。

首屏显示“继续上次”和最多三项有事实依据的建议。统一输入框支持文字，图片/链接复用现有导入；发送前显示将使用的资料范围。键盘弹出时输入栏可见，不与底栏重叠。

澄清问题一次一个，提供岗位候选或具体日期按钮。行动草稿以一张可折叠卡呈现“将更新 1 个投递、安排 2 个日程”，展开看差异、时间、提醒；底部只有“确认执行”“修改”“放弃”。高风险内容不藏在折叠摘要里。

保存中禁止重复确认；失败保留文字和草稿；重连先查询回执。成功卡可直接打开对应记录，退出助理后各页面刷新相同数据。只有实际完成数据库提交才显示成功。

复盘采用逐问短答：先问面试是否结束，再问最难的问题，再问自己的回答及下次行动。允许“先记原话，稍后整理”；不强迫一次填完整问卷，不用连续红点催促。

## 14. 分阶段路线图与验收

### P0a：修复与可信执行底座

范围：确认助理入口缺陷并补表单；建立持久化会话/草稿；提取必要业务写函数；补 Preparation 版本和事件轮次；统一确认幂等、原子事务、证据引用、错误回执。

验收：生成和刷新草稿不写正式数据；两设备修改后旧草稿报冲突；并发确认/断网重试只得到同一组记录；中间动作失败不留下部分记录；旧投递/日历保存回归通过。

### P0b：可快速上线的 MVP——聊天办事

范围：支持查询、投递新建/更新、日程新建/改期/完成，建立关联面试准备和用户选定资料的独立复用；多轮澄清和指代；手机确认卡；明确使用的上下文；使用统计与硬调用限额。日常主动价值先提供首页事实提示，不做后台模型日更。

首个上线切片：完整跑通“收到面试通知 → 识别正确岗位 → 面试/准备排期 → 绑定投递简历元数据与准备 → 确认 → 查看记录”。不把自动读取简历全文、复杂陪练和长期画像作为 MVP 发布前提。

验收数据集：至少 30 个匿名固定场景；10 个单意图、8 个跨模块、6 个日期/对象歧义、6 个重试/冲突/恶意资料场景。一般场景意图与目标匹配达到 90% 以上；安全关键场景必须全部阻止未授权/不确定写入。失败样例不得靠自动写入后人工修正达标。

关键用户验收：常见完整通知最多一次必要澄清和一次确认；375px 无横向溢出且键盘不遮确认区域；刷新可恢复；成功后其他页面可见同一记录。响应目标以实测 p95 记录，超时可恢复，不先承诺供应商无法保证的秒数。

### P1：面试教练与主动复盘

范围：真实面试复盘、确认后材料沉淀和行动安排；可管理长期记忆；按简历版本提取/确认正文；每日/每周、面试前后规则提示；可选邮件汇总；语义召回评测后增强检索。

验收：复盘原话与模型建议分开；新经历/数字必须补充确认；材料保存和后续日程同组幂等；过期/取消面试不再催促；每周期提示去重；没有邮件配置仍可使用站内提醒；清除记忆后下一轮不再召回；PDF 解析失败可粘贴正文，不能宣称已读。

### P2：按实际使用证据增强

范围：更好的跨公司材料召回和动态追问；可观测长任务恢复；基于已确认偏好调整计划建议；真实来源调研。邮箱同步、微信通知、系统日历作为独立授权项目，不绑定助理 MVP。
